# Рефакторинг: от прототипа к клиент-серверному приложению

Плана работ по фичам — `PLAN.md`. Здесь другое: как привести уже написанное к
устройству, в котором следующая фича стоит дешевле предыдущей, а не дороже.

Повод — накопленный долг прототипа: `engine.py` вырос до 3655 строк и держит в
себе семь несвязанных обязанностей, форма вызова из CLI стала внутренним API,
каждая операция читает стор целиком, а восемь страниц фронтенда — восемь
независимых императивных скриптов. Ни одна из этих вещей не мешает сегодня.
Все четыре дорожают линейно от каждой новой фичи.

Продукт, к которому идём: клиент-серверное приложение с быстрым фронтендом,
заточенное под ввод без утомительных действий. Пользователь — продвинутый,
работает быстро, заморачиваться не хочет. Из этого следует единственное
требование к интерфейсу, из которого выводится всё остальное: **ежедневный
цикл проходится без мыши, и любая запись отменяется в течение нескольких
секунд.**

> **Ревизия 2026-09-08.** Первая редакция писалась до среза 0. После него три
> пункта среза 1 закрыты, а по ходу вскрылось четыре вещи, которых в плане не
> было: задачи в API адресуются куском названия, ошибки ядра ходят через
> `sys.exit`, `server.py` не покрыт ни одним тестом, а «быстрый ввод без работы
> в ядре» не сходится с тем, как устроен разбор дат. Все четыре внесены в
> таблицу решений и в срезы. Срез 1 разрезан на три (ядро, HTTP, клиент), у
> каждого свой критерий приёмки. Сделанное отмечено, а не удалено.

## Принятые решения этого рефакторинга

| Решение | Обоснование |
|---|---|
| **Фронтенд — React 19 + TypeScript + Vite** | Пересматривает «не переезжаем на React/Vue» из `CLAUDE.md`: довод там стоял на «Node может не быть», и сам же документ его снял (Node ставим руками при развёртывании). React, а не Svelte — и это осознанная замена первой редакции этого документа, где стоял Svelte. Довод за Svelte был про вес бандла и виртуальный DOM, и **для этого приложения он не работает**: страница живёт на `127.0.0.1` и грузится с локального диска, а узкое место измерено и находится в бэкенде (полное чтение стора, 161→328 мс) — экономить 15 КБ и такты рендера там, где ждут 300 мс запроса, бессмысленно. Что действительно решает — список нужных интерфейсу вещей: палитра команд, доступные модалки с правильной клавиатурой и фокусом, оптимистичные мутации с откатом, виртуализация длинного завала. Под каждую в React-экосистеме есть отлаженное (`cmdk`, Radix, TanStack Query, TanStack Virtual), а руками мы это уже начали писать дважды: окно контроля продублировано в `feed.js` и `task.js`. Плюс код пишется в основном Claude Code, а React + TS представлен в обучении несопоставимо шире, чем Svelte 5 с рунами — при прочих равных это прямо влияет на цену каждой правки |
| Отдаём за React больше кода на тот же экран | Честная цена: хуки, массивы зависимостей, ручная забота о лишних рендерах — там, где Svelte обошёлся бы присваиванием. Плюс четыре библиотеки со своей сменой версий вместо нуля. Принимаем: каждая из четырёх заменяет то, что иначе пишется руками, и то, что руками в этом репозитории уже разошлось между страницами |
| **Сборка — на ноутбуке при обновлении, `dist` не в git** | Бандл платформо-независим (это обычные `.js`/`.css`), но коммит `dist` в main даёт нечитаемые диффы, распухшую историю и риск расхождения `src` и `dist` в одном коммите. В репозитории — `apps/web/src` и `package-lock.json`; скрипт обновления делает `git pull`, затем `npm ci && npm run build`, если менялся `apps/web/` или лок-файл |
| Сборка атомарна, предыдущий `dist` остаётся | Цена решения выше — сборке нужен npm-реестр, и упавшая сборка блокирует обновление. Собираем во временный каталог, подменяем только при успехе, прошлый `dist` держим как откат. Тогда упавшая сборка блокирует обновление, но не ломает работающее приложение — это ровно R6. Писать это **до** первой React-страницы, не после |
| **HTTP — FastAPI + Pydantic** | Контракт требует структурных ошибок с указанием поля (`CONTRACT.md`) — Pydantic даёт их вместе с путём поля бесплатно, вместо ручной сборки в каждой команде. Плюс схемы запросов и ответов становятся исполняемым контрактом, а не описанием в markdown, которое уже разошлось с кодом. Цена — три зависимости (`fastapi`, `pydantic`, `uvicorn`), все чистые Python-колёса, ставятся тем же `pip install -r`. Сервер по-прежнему слушает только `127.0.0.1` |
| **Порядок — вертикальный срез, не слой за слоем** | Один сценарий (лента → отметка шага) доводится сверху донизу и становится образцом, по которому переделывается остальное. Слой за слоем означает месяцы, в которые ничего не улучшилось для человека, и образец, проверенный только на себе |
| **Код английский, домен русский** | Идентификаторы, имена в API, схеме БД и CLI — английские. Русский остаётся в строках интерфейса, данных, пользовательских маршрутах (`/лента` и прочие — их видит человек, они не меняются) и **в комментариях**. Комментарии не переводим: в этом репозитории они несут обоснования решений и переписыванием на английский не покупается ничего |
| Дату и повторения не переписываем, а переносим | `parse_date_input` с разговорным временем и `recurrence.py` — самый проверенный код в репозитории (тождество `parse_text(describe(rule))` на 3000 случаях, 68 форм дней недели из 68). Они уже чистые функции. Переезжают файлом, логика не трогается |
| ~~Переход через прокси, без big-bang~~ → **FastAPI становится единственным сервером с первого дня** | Пересмотрено 2026-09-08. Все ~90 маршрутов `server.py` — трёхстрочные вызовы `engine.cmd_x(_args(...))`; перенести их в FastAPI-роутер механически, с тем же шимом `_args`, стоит день. Прокси стоил бы второго процесса, второго порта и трансляции ошибок на все три среза перехода. Дальше маршруты типизируются по одному по мере переезда команд в `core`; нетипизированный маршрут виден в коде по импорту шима. Цена: перенос без тестов опасен, поэтому ему предшествует golden-снимок ответов старого сервера (срез 1b) |
| **Задача в API адресуется `task_id`, не куском названия** | Сейчас `/api/action` шлёт `task: "<название>"`, а ядро ищет его через `find_task` подстрокой, тем же путём, что CLI. Для человека в консоли это удобно, для клиента это гонка: переименовал задачу в карточке, лента держит старое название, отметка уходит в «нет задачи». Стабильных ключей строк без id тоже не собрать. `tasks.id` уже есть (`store.TaskRef`); строки ленты, карточка и ответы записи несут `task_id`, поиск по куску названия остаётся в CLI-адаптере как удобство человека |
| **Ошибки ядра — типизированные исключения, не `sys.exit`** | Конфликт состояния («шаг уже done», «нет задачи») сегодня поднимается `sys.exit(text)` внутри `cmd_*`, а `server.py` ловит `SystemExit` в четырёх местах и в пятом забыть некому. `core` бросает `NotFound`, `Conflict`, `Ambiguous`, `ValidationError(field, message)`; `api` переводит их в 404/409/422 с прежним телом `{"ok": false, "errors": [...]}`, CLI — в код возврата 1 и текст в stderr. Контракт не меняется, меняется то, что его нельзя нарушить забытым `try` |
| **Типы клиента генерируются из OpenAPI** | FastAPI отдаёт `openapi.json`; `openapi-typescript` превращает его в `apps/web/src/api/schema.d.ts`. Файл в git, `make check` проверяет, что он свежий. Поле, добавленное в Pydantic-модель и забытое в клиенте, ловит `tsc`, а не заказчик |
| **Быстрый ввод требует работы в ядре** | Уточняет пункт 2 целевого UX, где стояло «новой работы на бэкенде — ноль». Проверено 2026-09-08: `parse_date_input("позвонить Василию завтра в полдесятого")` падает с `ValueError`, разбор принимает только строку целиком. Нужна `domain.extract_when(text)`: перебирает хвосты фразы от длинного к короткому, первый разобравшийся и есть дата; возвращает название, момент и границы совпадения для подсветки. Небольшая функция поверх готового разбора, и она же нужна R21 |
| **Причина у «не сделано» необязательна** | `server.py` требует причину для `notdone`, ядро её не требует (`_reason_error` пропускает пустую), а ТЗ (R15) называет комментарий к «не сделано» необязательным. Без этого клавиша `n` невозможна: одно нажатие превращалось бы в форму. Обязательной причина остаётся у `fail`, дата — у `defer` |
| Клиент: TanStack Query, react-router, Radix (Dialog, Toast), cmdk, react-hotkeys-hook; стили — CSS Modules на нынешних токенах из `style.css` | Каждая библиотека закрывает то, что в `static/` уже написано дважды. Tailwind не берём: палитра и тёмная тема уже описаны переменными, переписывать их на утилиты — работа без выигрыша |
| Тесты клиента: Vitest + Testing Library на редьюсер клавиатуры и мутации; один Playwright-сценарий «утро за десять нажатий» | Критерий готовности среза 1c должен быть исполняемым, иначе он останется фразой в документе |

## Что именно не так сегодня

Диагноз, а не впечатление: каждый пункт — с местом в коде.

### A. `engine.py` — модуль-бог

3655 строк, минимум семь несвязанных обязанностей в одном файле:

1. Доступ к стору (`get_store`, `load_tasks`, `find_task`)
2. **Мёртвый markdown-ввод-вывод**: `parse_file`, `write_file`, `PlainDumper`,
   `render_steps`, `put_steps_into_body`, `_strip_steps_block` — наследство
   домиграционной архитектуры, `pyyaml` держится в зависимостях ради него
3. Доменные вычисления (`task_status`, `current_steps`, `is_closed`,
   `stall_count`, `step_view`, `leaves_of`, `_closure`)
4. **Разбор русских дат и разговорного времени** — около 250 строк
   (`_месяц`, `_пол_часа`, `_четверть_часа`, `_без_минут`, `_разговорное_время`)
5. Валидация (`validate_new_task`, `validate_task_edit`, `resolve_steps`,
   `soft_warnings`)
6. Около шестидесяти `cmd_*` — прикладной слой
7. Выгрузка в Excel, бэкапы, вложения, база знаний, поиск, повторения

Следствие: любая правка трогает один файл; `test_engine.py` — 171 КБ, то есть у
тестов та же болезнь; а правило «пишет только движок» держится не структурой, а
тем, что всё лежит в одном месте. Границы, которую нельзя случайно перейти, нет.

### B. Форма вызова из CLI стала внутренним API

Все команды имеют вид `cmd_x(args, today)`, где `args` — argparse-Namespace.
HTTP вынужден его подделывать (`_args(**поля)` в `server.py`), из чего следует:

- HTTP-слой знает, какие флаги хочет каждая команда → `server.py` это ~90 ветвей
  `if route ==` с переписанными руками списками полей. Добавить поле — правка в
  двух местах, забыть одно — тихо.
- Ничего не типизировано. Имена полей — строки на двух языках через три слоя.
- Форма ошибки собирается руками в каждой команде.

Контракт этого не требует: `CONTRACT.md` говорит «операции», а не «argparse».

### C. Каждая операция читает стор целиком

`store.load_tasks()` — один запрос по задачам, плюс по два на каждую задачу
(шаги и теги), плюс по одному на каждый шаг (весь журнал). На целевом объёме из
`PLAN.md` (5120 задач, 11920 шагов) это около 22 тысяч запросов и полная сборка
истории — **на каждый вызов**, включая `/api/feed`, который историю не
показывает вообще. Измерено там же: 161 мс сейчас, 328 мс на 10 тысячах, рост
линейный. Запись идёт тем же путём и затем перезаписывает шаги и журнал задачи
целиком.

Индексы есть на `step_log`, `kb_links`, `attachments`, `tasks(cycle)`. Индекса
на `steps(status, control_date)` — то есть ровно на том, что спрашивает лента, —
нет.

Это самый крупный архитектурный пункт и единственный, который ухудшается сам.

**И худший его случай — `refresh`.** Замеры среза 0 (`tools/bench.py`, запись в
`PROTOCOL.md` от 2026-09-07) дали: лента 48 → 176 → 357 мс на 1250 → 5000 →
10000 закрытых задач, то есть ровно линейно, как и было записано. Но `refresh`
на тех же профилях — **21 и 71 секунда**. Он устроен как
`for task in load_tasks(): save(task, today)`, а `save_task` удаляет и
вставляет заново все шаги и все строки журнала задачи. Свой докстринг называет
эту запись «одной и той же дешёвой операцией».

Зовёт его `remind.py:156` безусловно, на каждом пробуждении, а планировщик
Windows будит `remind.py` каждые пять минут (`REMINDERS.md`). На целевом объёме
это 71 секунда из каждых 300 — четверть времени непрерывной записи в базу,
которая лежит под OneDrive и потому выгружается заново целиком.

Записывать при этом нечего. Сводка в БД не хранится, колонок под неё нет; ни
одно хранимое поле не зависит от «сегодня» (статус считается из шагов,
просрочка — из `control_date`); `render_steps`/`put_steps_into_body`, которые
раньше писали блок шагов в тело заметки, после переезда в БД не вызываются
ниоткуда. То есть `refresh` над нетронутым стором перезаписывает строки байт в
байт теми же. Побочно сжигает по 20 тысяч значений автоинкремента `step_log.id`
за прогон, из-за чего id строки журнала не стабилен между прогонами.

Вывод для порядка работ: это самая дешёвая правка с самым большим выигрышем в
проекте, и она идёт первой в срезе 1 — раньше ленты.

### D. Восемь страниц — восемь независимых скриптов

Около 150 КБ рукописного DOM. `common.js` — верный инстинкт, но несёт только
`fetch`/тост/`shortDate`/стор/`DateField`. Всё остальное дублируется: открытие и
закрытие модалок, отрисовка ошибок по пути поля, разметка строки, окно контроля
(`feed.js` и `task.js` реализуют одно и то же окно с четырьмя кнопками дважды —
`task.js:681` это прямо признаёт: «то же, что на ленте»), формы пачки, чипы
тегов. Роутинга и общего состояния нет, поэтому отметка на одной странице не
может обновить другую. После каждого действия — полный перерендер списка
(`replaceChildren` по всей ленте).

### E. Главный экран — только мышью

Вся клавиатурная работа ушла в форму создания: цепочки по Enter, Ctrl+Enter на
сохранение. У ленты — того, чем пользуются каждый день, — горячих клавиш нет
ни одной: чтобы отметить шаг, нужно взяться за мышь. Нет палитры команд, нет
быстрого добавления откуда угодно, нет `j`/`k`, нет `d`/`n` на строке под
фокусом.

Действия не оптимистичны: отметка → ждём POST → ждём полный `/api/feed` →
полный перерендер. И **отмены нет нигде**: `notdone`/`defer`/`fail` пишут в
журнал сразу, промах лечится только через карточку задачи. На отмену задачи
стоит `confirm()` — блокирующий системный диалог, который убивает клавиатурный
поток насмерть.

Для «продвинутого, который работает быстро», это главная дыра продукта — больше
любой из архитектурных.

### F. Контракт разошёлся с кодом в обе стороны

- `search` и `fail` помечены в `CONTRACT.md` как «нет» — а `cmd_search` и
  `cmd_fail` в коде есть и работают.
- Расхождение счётчиков переносов, которое `PLAN.md` держит открытым, **уже
  починено**: `task.js:273` показывает `stalled` от движка и сам не считает.
  Устарел документ, а не код.
- Восемь ключей настроек сохраняются, валидируются и показываются, но не
  читаются ни одним модулем (`PLAN.md`, «Что вылезло сквозным счётом»). Это
  хуже отсутствующей настройки: человек её меняет и делает вывод, что работает.
- Этап (b) базы знаний не начат: таблицы `kb_notes`/`kb_links` пусты, база
  живёт в `База/*.md`, и по записи в `PLAN.md` это **сломало** работавший R3.

### G. Рабочее дерево грязное

Около 25 изменённых файлов не закоммичены. Рефакторинг с этого начинаться не
может: нечем будет отличить свою правку от чужой.

## Целевое устройство

Слои те же четыре, что в `CLAUDE.md`, — они верны. Меняется то, что сейчас все
четыре живут в двух файлах. Зависимости строго в одну сторону:

```
apps/web/          React + Vite       ← единственный, кто знает про DOM
apps/cli/          argparse           ← тонкий адаптер
apps/remind/       cron               ← тонкий адаптер
api/               FastAPI + Pydantic ← схемы = контракт, единственный HTTP-слой
core/              use-cases: feed(), mark(), create_task(), undo_last()
domain/            чистые функции: статусы, даты, буксование, ru-даты, повторения
store/             SQLite: репозитории с запросами, а не load_tasks()
```

Правила, которые делают это устройством, а не картинкой:

- **`core` не знает ни про HTTP, ни про argparse.** Функции принимают
  типизированные модели и возвращают типизированный результат. `today` не
  протаскивается позиционно через сорок функций — внедряется `Clock`.
- **`api` только отображает HTTP ↔ core.** Роутинг — таблица, не цепочка `if`.
  Pydantic-модели дают структурные ошибки с путём поля, которых требует
  контракт.
- **`cli` и `remind` зовут те же функции `core`.** Тогда «форма и бот поймут

## Целевой UX: что значит «быстро и без заморочек»

Одно правило: **ежедневный цикл проходится без мыши, и любая запись отменяется
в течение нескольких секунд.** Из него семь пунктов.

1. **Палитра команд** (`Ctrl+K`): перейти к задаче, перейти на страницу,
   выполнить действие. Одна точка входа вместо восьми ссылок в шапке. Опирается
   на уже готовый `/api/search`.
2. **Быстрое добавление** (`a` откуда угодно, или прямо в палитре): одна строка
   «позвонить Василию завтра в полдесятого» → название плюс дата контроля,
   задача с одним шагом. Полная форма остаётся для цепочек. В первой редакции
   здесь стояло «новой работы на бэкенде — ноль» и клавиша `n`; оба
   исправлены: разбор принимает только строку целиком, поэтому нужна
   `domain.extract_when` (см. таблицу решений), а `n` занята «не сделано».
3. **Клавиатура в ленте**: `j`/`k` или стрелки — фокус, `d` — сделан, `n` — не
   сделан, `t` — перенести (открывает поле даты уже в фокусе), `f` — провален,
   `Enter` — карточка, `Esc` — закрыть. Отметка шага становится одним нажатием.
4. **Оптимистичная отметка и отмена в тосте.** Строка меняется сразу, тост
   говорит «Сделано · Отменить (5)». Требует настоящей операции `undo` в ядре —
   см. ниже. Без неё пункт был бы обманом: запись уже в журнале.
5. **Разбор завала как клавиатурная очередь.** Последовательный режим уже есть;
   дать ему те же `d`/`n`/`t`/`f` и одно поле даты — завал из пятнадцати
   пунктов разбирается пятнадцатью нажатиями.
6. **Никаких блокирующих диалогов.** `confirm()` уходит; вместо него — либо
   встроенное подтверждение, либо та же отмена в тосте.
7. **Никогда не перерисовывать список целиком.** Стабильные `key` по
   `task+step` и мемоизация строки — тогда отметка перерисовывает одну строку,
   а не всю ленту, как `replaceChildren` сегодня.

Карта клавиш, чтобы не спорить о ней в коде. Три области: лента (и очередь
завала), диалог, палитра. Клавиша действует только в своей области: `d` в
открытом диалоге не отмечает строку под фокусом.

| Клавиша | Где | Что делает |
|---|---|---|
| `j` / `k`, `↓` / `↑` | лента, завал | фокус по строкам |
| `d` | строка под фокусом | сделан |
| `n` | строка | не сделан, без причины; дату +1 ставит ядро |
| `t` | строка | перенести: диалог с полем даты в фокусе, `1`–`4` пресеты, `Enter` сохраняет |
| `f` | строка | не будет сделано: диалог с причиной в фокусе |
| `Enter` | строка | карточка задачи |
| `u` | везде | отменить последнюю отметку, пока виден тост |
| `a` | везде | быстрое добавление одной строкой |
| `/` | везде | поиск |
| `Ctrl+K` | везде | палитра команд |
| `Esc` | диалог, палитра | закрыть; в очереди завала это пауза, не ответ |

Что из этого требует работы в ядре — а требует немного, и оно там и должно быть:

- ~~**Операция `undo`.**~~ **Сделано 2026-09-07** — `engine.cmd_undo`, шестое
  действие в `/api/action`, подкоманда CLI, строка в `CONTRACT.md`. Вышло с
  двумя отличиями от задуманного здесь. Первое: запись из журнала
  **удаляется**, а не гасится обратным событием — иначе промах навсегда портил
  бы счётчик буксования, а тот в этом продукте сигнал «нужен другой ход», а не
  украшение. Второе: окно — «сегодня», а не «несколько секунд», потому что в
  `step_log` лежит дата без времени; точнее имеющимися данными не отмерить.
  Открытый вопрос, оставленный сознательно: `done`/`skip`/`fail` попутно ставят
  дату контроля шагам, которые от них открылись и своей даты не имели, а откат
  их не снимает — в журнале не записано, каким шагам они достались. В
  интерфейсе не видно (отменённый шаг снова открыт, следующие не активны), тест
  это поведение пиннит. Точный откат потребует поля в `step_log`.
- **Ответ на запись несёт новое состояние.** `mark()` возвращает обновлённую
  строку и счётчики, чтобы клиенту не нужен был второй круг до сервера. Это
  контрактно чистая версия оптимистичного UI: оболочка по-прежнему ничего не
  вычисляет — она получает новое состояние вместе с записью.
- **`fail` и `search` просто отметить в контракте как существующие.**
- **`task_id` в строках ленты и в операциях записи.** Без него нет стабильных
  ключей строк, а переименование задачи в одной вкладке ломает отметку в
  другой (см. таблицу решений).
- **`extract_when` для быстрого ввода** и **необязательная причина у
  `notdone`** — обе строки в таблице решений; без них пункты 2 и 3 выше не
  собираются.

Признак готовности, по которому проверяем себя, а не ощущение: **утренний
разбор десяти шагов — десять нажатий, без мыши, ни одного ожидания дольше
100 мс.**

каждого `mark` на профиле 10 000 закрытых из `tools/bench.py`, порог 100 мс.
Это первый срез, который меняет день заказчика, и его надо показать.

### Срез 2. Запись: быстрый ввод, форма, карточка, шаблоны. ~2 недели

- `core/tasks.py`: `create_task`, `update_task`, `cancel`, `close`, `reopen`,
  `delete` над Pydantic-моделями. `validate_new_task`, `validate_task_edit`,
  `resolve_steps` переезжают в `domain/steps_plan.py`; список ошибок с путём
  поля (`steps[2].control_date`) собирает Pydantic. Списки полей из
  `server.py._create` и `_task_update` исчезают.
- `core/templates.py` над `templates.py`; `recurrence.py` переезжает в
  `domain/` файлом, логика не трогается.
- Клиент: быстрый ввод по `a` и из палитры через `extract_when` с подсветкой
  распознанной части; полная форма портируется с сохранением клавиатурной
  цепочки (Enter → дата → следующий шаг, Ctrl+Enter); карточка задачи с
  редактором шагов и **тем же компонентом** диалога контроля, второй экземпляр
  окна из `task.js` исчезает; шаблоны с предпросмотром дат и разбором
  повторения словами; вложения через `multipart` (`UploadFile` в FastAPI)
  вместо base64 в JSON, ограничение размера остаётся в `attachments.save`.
- Удаляются `static/index.html`, `app.js`, `task.*`, `templates.*` и их
  маршруты в `api/legacy.py`.

### Срез 3. Чтение: все задачи, архив, база знаний, настройки. ~1,5 недели

Механическая работа по образцу. `list` и `archive` получают запросы в `store`
со счётчиком буксования агрегатом в SQL: сейчас они линейны от архива, это
записано в `PROTOCOL.md`. В настройках выводятся только четыре живые группы,
мёртвые ключи решаются в срезе 4. Каждая страница удаляет свой `.js` и свои
маршруты в `legacy.py`; после последней `legacy.py` и `static/` пусты и
удаляются.

### Срез 4. Уборка, которая становится возможной только теперь

- Удалить markdown-ввод-вывод из движка (`parse_file`, `write_file`,

- Разрезать `test_engine.py` по границам новых модулей.
- Восемь мёртвых ключей настроек: подключить или удалить. Третьего нет.
- База знаний, этап (b): доделать или явно припарковать письменно — с записью,

- `CONTRACT.md` сводится к правилам и ссылке на `/docs`: таблицы операций

- `step_log` получает колонку времени (схема 4): окно `undo` становится

## Чего не делать

- **Не переписывать разбор дат и повторения.** Перенести файлом.
- **Не трогать схему стора** дальше добавления индексов, пока срез 1 не
  подтвердит форму запросов.
- **Не переводить комментарии** и не переименовывать данные и пользовательские
  маршруты.
- **Не делать big-bang.** Каждый срез отгружается отдельно за счёт
  `api/legacy.py` с механически перенесёнными маршрутами и старых страниц,
  живущих рядом с новыми, пока их не заменили.
- **Не начинать фронтенд до замеров среза 0.**

## Риски

- **Два фронтенда сосуществуют.** На время срезов 1–3 живут и старые страницы,
  и новая лента. Принять, держать шапку работающей в обоих, и не растягивать
  дольше двух срезов.
- **Сборка на его ноутбуке падает.** Атомарная подмена и сохранённый прошлый
  `dist` — вся защита, и она пишется до первой React-страницы.
- **FastAPI против R5** («без сложной инфраструктуры»). Три чистых
  Python-зависимости, тот же `pip install -r`, тот же `127.0.0.1`. Но это
  пересмотр записанного решения, и в `CLAUDE.md` он должен появиться строкой с
  обоснованием, а не молча.
- **Главный риск не изменился с `PLAN.md`: заказчик до сих пор не завёл ни
  одной настоящей задачи.** Каждое утверждение про UX в этом документе —
  гипотеза о том, как он работает. Срез 1 нарочно мал: его можно показать и
  оказаться неправым дёшево.
- **Две поверхности API в переходе.** `/api/*` для старых страниц и
  `/api/v1/*` для нового клиента живут вместе на срезах 1c–3. Правило одно: в
  `legacy.py` ничего не дописывать.
- **Golden-снимок старого сервера ловит только то, что в него положили.**
  POST-сценарии составляются руками; смягчение записано в срезе 1b — список
  маршрутов сверяется с `server.py` до его удаления.
- **Переезд на `task_id` меняет форму ответов.** Старые страницы продолжают
  слать название через `legacy.py`, новые поля они игнорируют; CLI получает
  `task_id` в ответах как дополнение. Ломающих изменений для бота нет, но
  `INTEGRATION.md` должен это записать в срезе 1a, а не в срезе 5.
