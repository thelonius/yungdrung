# Контракт для OpenClaw-инстанса

Как бот разговаривает с движком. Всё, что здесь описано, проверено вызовами, а не
предположено.

Бот — это слой 3 из `CLAUDE.md`: чат в Telegram, утренняя сборка, разбор
свободного текста. Он живёт на том же ноутбуке, что и вольт, и обращается к
движку как к обычной программе командной строки.

## Главное правило

**Бот не пишет в `.md` напрямую. Никогда.** Всё, что меняет задачи и шаги, идёт
через `engine.py`. Иначе получается два писателя одного файла, и вольт с доской
в Obsidian разъезжаются — ровно то, от чего защищает вся конструкция.

Читать файлы вольта бот может, но и это лишнее: `list`, `next` и `show` отдают то
же самое разобранным JSON.

## Как вызывать

```python
import json, subprocess

def движок(*аргументы, вольт=None):
    рез = subprocess.run(
        ["python", "engine.py", *аргументы],
        capture_output=True,
        text=True,
        encoding="utf-8",          # обязательно, см. ниже
        env={**os.environ, "YUNGDRUNG_VAULT": вольт} if вольт else None,
    )
    if рез.returncode != 0:
        raise RuntimeError(рез.stderr.strip())
    return json.loads(рез.stdout)
```

Что здесь важно и не подлежит упрощению:

- **`encoding="utf-8"` обязателен.** Движок печатает UTF-8 всегда, независимо от
  кодировки консоли — иначе на Windows падала бы сама печать русского текста. Но
  `subprocess` по умолчанию декодирует в кодировке локали, и на Windows это
  cp1251: «Грант» молча превращается в «Ð“Ñ€Ð°Ð½Ñ‚». Поймано настоящим прогоном на
  машине заказчика, не выдумано.
- **Код возврата 0 — успех, 1 — ошибка.** Текст ошибки идёт в `stderr`,
  человеческим языком: `нет задачи по «грант»`, `шаг 2 уже done`. В `stdout` при
  ошибке ничего не попадает, так что `json.loads` не надо оборачивать в защиту от
  мусора.
- **Путь к вольту** — переменная окружения `YUNGDRUNG_VAULT`. По умолчанию папка,
  где лежит `engine.py`.

## Что нужно боту

### Утренняя сборка

```
refresh   → пересчитать статусы (задача просрочена оттого, что прошёл день)
next      → что требует внимания сегодня
```

`refresh` перед `next` обязателен, иначе сборка соберётся по вчерашним статусам.
Файлы без изменений не переписываются, лишней записи не будет.

`next` отдаёт:

```json
{
  "today": "2026-08-13",
  "due": [
    {
      "task": "Замена подшипника в колесе",
      "step": 2,
      "title": "Снять колесо, заменить",
      "control_date": "2026-08-12",
      "overdue_days": 1,
      "stalled": 3,
      "last_reason": "мастер в отпуске до сентября",
      "status": "overdue"
    }
  ],
  "stalled": [ ... ]
}
```

`status`: `overdue` — просрочено, `due` — сегодня, `no_date` — шаг открыт, но
дата не назначена. `stalled` — сколько раз шаг отмечали «не сделан»; те же
записи, где счётчик дошёл до трёх, продублированы в отдельном списке `stalled`.
Их стоит показывать иначе: четвёртый перенос подряд значит, что нужен другой ход,
а не новая дата.

Поле `task` — это имя файла без расширения. Оно же идентификатор для всех команд
ниже: их аргумент ищется по куску имени, поэтому передавать надо значение `task`
целиком, а не «грант».

### Отметки шагов

```
done    <задача> <шаг> [--reason ...]
notdone <задача> <шаг> [--reason ...] [--to ГГГГ-ММ-ДД]
defer   <задача> <шаг> --to ГГГГ-ММ-ДД [--reason ...]
skip    <задача> <шаг> [--reason ...]
```

Разница между `notdone` и `defer` — в том, кто назначил дату. `defer` — решение
заказчика, он называет день. `notdone` — обстоятельства (не дозвонился, человек в
отпуске, было некогда); шаг остаётся открытым, движок сам переспрашивает завтра,
а причина копится в истории. Кнопки под утренней сборкой должны давать оба
варианта, иначе счётчик буксования не наберётся и мы не увидим застрявшие дела.

Ответ `notdone`:

```json
{
  "ok": true, "task": "...", "step": "2", "status": "pending",
  "next_check": "2026-08-14", "stalled": 4,
  "hint": "шаг буксует, нужен другой ход"
}
```

`hint` появляется только когда есть что сказать — его можно показывать как есть.
После `done` в ответе приходит `next_step`: название следующего шага, если он
есть. Это то, что заказчик просил показывать сразу после отметки.

### Всё остальное

```
list              все задачи со статусами и прогрессом
show <задача>     одна задача целиком, включая историю каждого шага
export --to f.xlsx выгрузка в Excel тремя листами
```

## Чего в движке пока нет

**Создать задачу нельзя.** Команд ровно девять: `next`, `list`, `refresh`,
`show`, `done`, `notdone`, `defer`, `skip`, `export`. Задачи заводятся руками в
Obsidian.

Для бота это дыра: R9 в ТЗ — «заказчик пишет боту свободным текстом, бот
раскладывает написанное на задачи». Разложить бот сможет, а записать — нет.
Варианта два, и выбирать надо до того, как писать бота:

1. Добавить движку команду создания, принимающую разбор на входе. Правило
   «единственный писатель» сохраняется.
2. Разрешить боту писать файл задачи самому. Проще на день работы, но заводит
   второго писателя в вольт со всеми последствиями.

Первый вариант правильный, второй дешёвый. Решать не здесь.

## Про язык ответов

В JSON статусы приходят по-английски (`overdue`, `waiting`, `done`) — это
машинный интерфейс. В самих файлах вольта они по-русски, потому что те файлы
читает заказчик. Не перепутать: для показа человеку переводить надо на стороне
бота, английские ключи наружу не показывать.
