# Контракт для OpenClaw-инстанса

Как бот разговаривает с движком. Всё, что здесь описано, проверено вызовами, а не
предположено.

Бот — это слой 3 из `CLAUDE.md`: чат в Telegram, утренняя сборка, разбор
свободного текста. Он живёт на том же ноутбуке, что и стор, и обращается к
движку как к обычной программе командной строки.

## Главное правило

**Бот не пишет в стор напрямую. Никогда.** Всё, что меняет задачи и шаги, идёт
через `engine.py` (или HTTP API `server.py`, который сам зовёт движок). Иначе
получается два писателя одной базы — ровно то, от чего защищает вся конструкция.

Читать файлы стора бот может, но и это лишнее: `list`, `next` и `show` отдают то
же самое разобранным JSON.

## Как вызывать

```python
import json, subprocess

def движок(*аргументы, стор=None):
    рез = subprocess.run(
        ["python", "engine.py", *аргументы],
        capture_output=True,
        text=True,
        encoding="utf-8",          # обязательно, см. ниже
        env={**os.environ, "YUNGDRUNG_VAULT": стор} if стор else None,
    )
    if рез.returncode != 0:
        raise RuntimeError(рез.stderr.strip())
    return json.loads(рез.stdout)
```

Что здесь важно и не подлежит упрощению:

- **`encoding="utf-8"` обязателен.** Движок печатает UTF-8 всегда, независимо от
  кодировки консоли — иначе на Windows падала бы сама печать русского текста. Но
  `subprocess` по умолчанию декодирует в кодировке локали, и на Windows это
  cp1251: «Грант» молча превращается в «Ð“Ñ€Ð°Ð½Ñ‚». Поймано настоящим прогоном на
  машине заказчика, не выдумано.
- **Код возврата 0 — успех, 1 — ошибка.** Текст ошибки идёт в `stderr`,
  человеческим языком: `нет задачи по «грант»`, `шаг 2 уже done`. В `stdout` при
  ошибке ничего не попадает, так что `json.loads` не надо оборачивать в защиту от
  мусора.
- **Путь к стору** — переменная окружения `YUNGDRUNG_VAULT`. По умолчанию папка,
  где лежит `engine.py`.

## Что нужно боту

### Утренняя сборка

```
next      → что требует внимания сегодня
```

Одна команда, а не две. **`refresh` перед `next` не нужен** — здесь раньше было
написано, что он обязателен, «иначе сборка соберётся по вчерашним статусам», и
это было неверно: `next` (как и `feed`, `list`, `show`) считает статусы и
просрочку сам, от переданной даты, при каждом вызове. В базе статус не хранится
— хранить его было бы вторым источником правды рядом с шагами.

`refresh` остался как диагностика: «покажи сводку по всем задачам на такой-то
день». Он ничего не пишет, и звать его в цикле незачем — на пяти тысячах задач
это лишние 190 мс чтения всего стора.

`next` отдаёт:

```json
{
  "today": "2026-08-13",
  "due": [
    {
      "task": "Замена подшипника в колесе",
      "step": 2,
      "title": "Снять колесо, заменить",
      "control_date": "2026-08-12",
      "overdue_days": 1,
      "stalled": 3,
      "last_reason": "мастер в отпуске до сентября",
      "status": "overdue"
    }
  ],
  "stalled": [ ... ]
}
```

`status`: `overdue` — просрочено, `due` — сегодня, `no_date` — шаг открыт, но
дата не назначена. `stalled` — сколько раз шаг отмечали «не сделан»; те же
записи, где счётчик дошёл до трёх, продублированы в отдельном списке `stalled`.
Их стоит показывать иначе: четвёртый перенос подряд значит, что нужен другой ход,
а не новая дата.

Поле `task` — это имя файла без расширения. Оно же идентификатор для всех команд
ниже: их аргумент ищется по куску имени, поэтому передавать надо значение `task`
целиком, а не «грант».

### Отметки шагов

```
done    <задача> <шаг> [--reason ...]
notdone <задача> <шаг> [--reason ...] [--to ГГГГ-ММ-ДД]
defer   <задача> <шаг> --to ГГГГ-ММ-ДД [--reason ...]
skip    <задача> <шаг> [--reason ...]
```

Разница между `notdone` и `defer` — в том, кто назначил дату. `defer` — решение
заказчика, он называет день. `notdone` — обстоятельства (не дозвонился, человек в
отпуске, было некогда); шаг остаётся открытым, движок сам переспрашивает завтра,
а причина копится в истории. Кнопки под утренней сборкой должны давать оба
варианта, иначе счётчик буксования не наберётся и мы не увидим застрявшие дела.

Ответ `notdone`:

```json
{
  "ok": true, "task": "...", "step": "2", "status": "pending",
  "next_check": "2026-08-14", "stalled": 4,
  "hint": "шаг буксует, нужен другой ход"
}
```

`hint` появляется только когда есть что сказать — его можно показывать как есть.
После `done` в ответе приходит `next_step`: название следующего шага, если он
есть. Это то, что заказчик просил показывать сразу после отметки.

### Группы подшагов

Шаг может быть группой: у неё `mode` («par» — подшаги в любом порядке, «seq» —
по очереди) и вложенный список `steps`; даты, статус и журнал есть только у
листьев, закрытие группы вычисляется из детей. В `create`/`update` группа
передаётся вложенно:

```json
{"title": "Подписи", "mode": "par", "steps": [
  {"title": "Подпись Говнова", "control_date": "2026-08-20"},
  {"title": "Подпись банка", "control_date": "2026-08-22"}
]}
```

Следствия для бота:

- `feed`/`next` могут отдать несколько строк одной задачи разом — по строке на
  каждый активный лист; название группы приходит полем `group`.
- Отмечается лист, не группа: `done <задача> <id группы>` — ошибка с кодом 1.
- После `done` дату «сегодня» могут получить сразу несколько открывшихся
  подшагов: их id приходят списком `dates_assigned`; старое поле
  `date_assigned_to_step` осталось и несёт первый из них.
- `show` отдаёт шаги плоским списком с полями `parent`/`mode` и вычисленным
  `closed` у каждого шага.

### Вложения

Файлы — картинки схем, сканы — привязываются к задаче или к шагу. Бот вызывает
не JSON-командой из этого файла, а прямым HTTP: `POST /api/attachments-add` с
телом `{"task": "...", "step": 2, "filename": "скан.pdf", "data": "<base64>"}`
(`step` опускается для вложения на всю задачу), `GET /api/attachments?task=...`
для списка, `GET /вложение/<id>` — сами байты. Инлайновым типам (картинки,
PDF) отдаётся настоящий `Content-Type` для показа прямо в чате; всё остальное —
принудительно на скачивание, независимо от того, что записано как MIME файла.

Запись базы знаний как владелец вложения пока не поддержана — ждёт переезда
`kb_notes` на БД (PLAN.md, спринт 1, этап b).

### Всё остальное

```
list              все задачи со статусами и прогрессом
show <задача>     одна задача целиком, включая историю каждого шага
export --to f.xlsx выгрузка в Excel тремя листами
```

## Битые записи

`list`, `next` и `refresh` возвращают поле `broken` — задачи, которые не удалось
разобрать:

```json
"broken": [{"task": "Заявка на грант", "error": "..."}]
```

**`broken` в утренней сборке надо показывать, а не игнорировать**. Иначе задача
молча исчезает из трекера.

Код возврата при этом остаётся 0: остальные задачи прочитались, команда сделала
своё дело. Пустой `broken` — норма.

## Чего в движке пока нет

**Создать задачу через CLI нельзя** — для этого есть веб-форма `/новая` и
`POST /api/create`. Команд ровно девять: `next`, `list`, `refresh`,
`show`, `done`, `notdone`, `defer`, `skip`, `export`.

Для бота это дыра: R9 в ТЗ — «заказчик пишет боту свободным текстом, бот
раскладывает написанное на задачи». Разложить бот сможет, а записать — нет.
Варианта два, и выбирать надо до того, как писать бота:

1. Добавить движку команду создания, принимающую разбор на входе. Правило
   «единственный писатель» сохраняется.
2. Разрешить боту писать файл задачи самому. Проще на день работы, но заводит
   второго писателя в стор со всеми последствиями.

Первый вариант правильный, второй дешёвый. Решать не здесь.

## Про язык ответов

В JSON статусы приходят по-английски (`overdue`, `waiting`, `done`) — это
машинный интерфейс. В самих файлах стора они по-русски, потому что те файлы
читает заказчик. Не перепутать: для показа человеку переводить надо на стороне
бота, английские ключи наружу не показывать.
