# Yungdrung — трекер задач

Контекст для Claude Code. Дальше править по ходу.

## Что строим

Локальный трекер задач с последовательными шагами и контрольным временем.
Задача = сущность с вручную заданной цепочкой шагов. Наступает время контроля →
система спрашивает про шаг → отметка «сделан / не сделан / перенести» → показывается
следующий шаг. Все шаги выполнены → задача закрывается.

Плюс база знаний в том же хранилище: термины в задачах ссылаются на заметки
(`[[Василий Говнов]]` → заметка про него).

## Что НЕ строим

- Не строим свой markdown-редактор, свой граф ссылок, свой поиск — это Obsidian
- Не строим свой планировщик-демон — это cron OpenClaw
- Не строим свой канбан-рендер — это Bases (доска приезжает сторонним плагином
  представления, в ядре её нет — см. решение ниже)
- Аудит существующих Excel-финмоделей — пока вне скоупа, решение отложено.
  Генерация черновиков финмоделей (R12 в ТЗ) — наоборот, в скоупе.

## Архитектура

Четыре слоя, связь только сверху вниз:

1. **Вольт** — единственный источник правды. Задачи — в SQLite (`вольт.db`),
   заметки базы знаний — в markdown (`База/`). Работает без сети, читается любым
   скриптом. Сами данные в git не версионируются, версионируется только код
   движка — см. «`Задачи/` и `База/` в git не отслеживаются» в решениях ниже.
2. **Движок шагов** — детерминированный модуль. Единственный, кто пишет шаги и даты.
   Без LLM. CLI-интерфейс, JSON на выходе.
3. **Интерфейсы** — сменные: Obsidian + Bases (обзор, канбан, навигация по ссылкам),
   чат OpenClaw (напоминания и отметки шагов).
4. **cron** — будит движок по расписанию.

Проверка на здоровье: если убрать слой 3 и 4 целиком, трекер должен продолжать
работать — данные на месте, движок считает просрочки, файлы правятся руками.

### Про «чат OpenClaw» (слой 3) и агрегацию из Telegram

Это не наш существующий чат-инстанс OpenClaw, а отдельный инстанс: своя
Telethon-сессия, заходит в те же telegram-чаты, что и человек, для сбора
информации к обработке. Дальше этот инстанс целиком передаётся человеку —
он будет крутиться на его виндовом ноутбуке, не у нас.

Следствия для архитектуры:
- Слой 3 (интерфейс) для этого случая — не просто «чат», а отдельный
  разворачиваемый компонент со своей Telegram-сессией. Схему хранения
  сессии, авторизацию, формат передачи на Windows — не проектировать
  заранее, решать когда дойдём до этого слоя.
- Слой 1 и 2 (вольт, движок) не должны знать про Telegram вообще — они
  получают информацию через тот же файловый интерфейс, что и любой другой
  клиент. Совместимость с передачей на чужую машину — лишний повод не
  протекать Telegram-специфику вниз по слоям.
- По дорожной карте («Первые шаги» ниже) этот слой не в первой итерации:
  сначала схема данных и движок работают без сети и без чата.

## Принятые решения

| Решение | Обоснование |
|---|---|
| ~~Markdown-вольт, не SQLite~~ → **SQLite** | Пересмотрено: вольт правится руками, поэтому недопустимые состояния достижимы. `is_closed()` и `BROKEN` в движке — заплатки на этой дыре, и площадь её растёт с каждой фичей. В базе с формой печатать неправильно нечего |
| Слово «вольт» в коде и документах — не жанр хранения, а имя папки | После перехода задач на SQLite задачи хранятся в файле `вольт.db` — это база данных, а не Obsidian-вольт. Название «вольт» (`VAULT`, `engine.VAULT`, `YUNGDRUNG_VAULT`) осталось от домиграционной архитектуры и обозначает каталог данных целиком: SQLite задач + markdown база знаний (`База/`) + вложения + шаблоны. Говоря о хранилище задач конкретно — это «база данных» или `вольт.db`, а не «вольт» |
| Данные локально, LLM онлайн ок | Без сети трекер не умирает, просто молчит |
| Шаги — YAML во frontmatter | Шагу нужны свои свойства: дата контроля, статус, переносы |
| Шаги не редактируются в UI Obsidian | Редактор свойств не тянет массивы объектов; пишет только движок |
| Bases, не классический Kanban-плагин | Kanban-плагин держит доску отдельным файлом → два источника правды |
| ~~Интерфейс — Obsidian~~ → **своя веб-морда** | Пересмотрено: ТЗ (5.7, 5.8) требует синонимы, подтверждённые ссылки и смещения в тексте — это писать всё равно нам, `[[ссылки]]` Obsidian их не умеют. Взамен платили неконтролируемой правкой файлов. Obsidian может остаться читалкой заметок, но продукт на него не опирается |
| Начинаем с таблицы Bases, не с доски | В ядре Bases четыре представления (таблица, список, карточки, карта), доски нет; группировка по статусу даёт то же самое без плагинов |
| Сводка задачи дублируется в свойства верхнего уровня | Bases и вики-ссылки не заглядывают внутрь массива `steps`; статус, текущий шаг и дата контроля должны быть отдельными полями |
| Движок рендерит шаги списком в тело заметки | В панели свойств Obsidian массив объектов виден обрезанным JSON — «провалиться в задачу» упиралось в нечитаемое. Блок между маркерами принадлежит движку, остальное тело — заказчику |
| Ссылки `[[...]]` в названиях шагов работают через тело | Во frontmatter Obsidian их не резолвит, а отрендеренный в тело список — обычный markdown, ссылки живые |
| В блоке шагов не чекбоксы, а значки | Чекбокс в Obsidian кликабельный: заказчик отметил бы шаг мышкой, движок затёр бы при следующей записи — два писателя одного поля |
| LLM-клиент — паттерн OpenAI SDK + `base_url` | Тот же паттерн уже в `~/mlops_tutor/app.py` и `~/svland/api/` — не изобретать заново |
| Не Groq | Проверено вживую: оба найденных Groq-ключа протухли (`expired_api_key`) — бесплатный тир умирает по времени |
| LLM-провайдер — NVIDIA NIM | OpenAI-совместимый (`integrate.api.nvidia.com/v1`), ключ переиспользован из `openclaw/workspace/.env`, проверен живым запросом |
| Dataview не использовать | Legacy, вытесняется нативными Bases |
| Статус задачи вычисляется из шагов | Иначе доска и шаги расходятся |
| Атомарная запись (temp + rename) | Obsidian кэширует и держит файлы открытыми — возможны гонки |
| Код доставляется git, артефакты — Telegram | Разные каналы для машины и человека; код через Telegram лишён версий и доставляется по частям |
| `git pull` выполняет OpenClaw, не заказчик | Заказчик git не видит и не ставит — сложность остаётся на нашей стороне |
| Секреты и вольт — не в общем репозитории | Telethon-сессия = полный доступ к аккаунту; его данные принадлежат ему |
| `Задачи/` и `База/` в git не отслеживаются | Иначе его рабочие дела уезжают на GitHub при `git add -A`, а наша правка тех же файлов ломает ему `git pull` конфликтом. Примеры — в `примеры/` |
| Вывод движка всегда UTF-8 | Кодировка консоли Windows другая; кто разбирает JSON — читает как UTF-8 явно (`encoding="utf-8"` в subprocess), иначе русский текст молча превращается в «Ð“Ñ€Ð°Ð½Ñ‚» |
| Ежедневный цикл — без LLM | Выборка по датам и статусам не требует модели; без сети трекер работает целиком |
| В LLM уходит только произвольный текст | Граница проходит по тому, надо ли понимать связную речь |
| Отметки шагов — кнопками, не текстом | Кнопка замыкает цикл S11 на машине заказчика: наружу не уходит ничего |
| Доставка напоминаний — сменный канал | Системный тост, телеграм и открытая страница за одним интерфейсом. Заблокируют телеграм — переключаем канал, работа не встаёт |
| Трей не нужен, хватает Планировщика Windows | Единственная работа трея — жить в фоне и показывать уведомления; планировщик делает и то и другое штатно, переживает перезагрузку и не тянет второй рантайм |
| Шаг — лист или группа подшагов (`par`/`seq`) | Заказчик вживую упёрся в «порядок не важен». Даты и отметки только у листьев, закрытие группы вычисляется; лента отдаёт строку на каждый активный лист. Одна глубина в формах, хранение — `parent_id`/`mode` в `steps` |
| Миграции схемы БД — `PRAGMA user_version` | База заказчика не синхронизирована с нашей: код едет через `git pull`, файл дорастает сам при первом открытии, данные не переписываются |
| Разбор «каждый вторник» — свой код, не LLM | Готового под русский нет: `recurrent` англоязычный по заявлению автора, у Duckling повторения — открытый тикет с 2014-го и Haskell-сервис в придачу, `rrule.js fromText` сам себя объявляет неполным. Своё же — словарь на два десятка слов, а не связная речь, то есть наша сторона границы. Плюс разбор дёргается на каждое нажатие клавиши и обязан работать без сети |
| Морфология повторений — таблицы основ, не pymorphy3 | Измерено: ручные основы берут 68 форм дней недели из 68 и 115 форм месяцев из 115. pymorphy3 (он в зависимостях ради базы знаний) для «воскресенья» ставит первой леммой «воскресение» — пришлось бы перебирать разборы в обход его ранжирования, платя 60–120 мс за загрузку словарей. Полноту сторожит тест: pymorphy3 порождает парадигмы, разбор обязан их взять |
| `parse_text` — обратное к `describe`, и это проверяется | Тождество `parse_text(describe(rule)) == rule` на 3000 случайных правил. Добавить поле в одну функцию и забыть про другую после этого нельзя |
| Не переезжаем на React/Vue | Код едет на виндовый ноутбук через `git pull`, сервер — `http.server` из стандартной библиотеки. Фреймворк означает Node с npm на его машине (а что там установлено — до сих пор открытый вопрос) или коммит бандла, от которого диффы нечитаемы. Настоящая проблема не в отсутствии фреймворка, а в дублях между страницами — лечится общим модулем. Preact или Alpine подключаются одним `<script>` без сборки, если станет тесно |
| Вложения шаблона копируются в заведённую задачу | Смотрит человек в задачу, а не в карточку шаблона. Копируется строка в таблице, не байты: файл адресуется своим sha256, поэтому вторая ссылка на ту же картинку ничего не весит |
| Сдвиги шагов шаблона вводятся приращениями, хранятся от старта | Процедуру описывают промежутками («позвонить, через три дня подготовить»), а хранение от старта обязательно: иначе правка одного шага молча двигала бы все следующие. Складывает промежутки страница — календаря в сумме чисел нет, он остаётся за ядром |
| Вложения адресуются содержимым (sha256), не путём и не именем | Та же картинка под другим именем — не вторая копия; поиск перед записью (`attachments.locate`) идёт по хешу, не по имени файла — версия, завязанная на имя, дедуп ломала |
| Вложения — своё зеркало в бэкапе, не в zip-архиве копии | Картинки не жмутся, ротация N копий не должна умножать их вес N раз; `backup.mirror_attachments` докапывает недостающее при каждом вызове `backup()` независимо от расписания zip-снимка |

## Где проходит граница LLM

Движок отвечает сам, наружу не уходит: утренняя сборка, просрочки, отметки шагов,
срезы по канбану и категориям, история задачи, выгрузка в Excel.

Уходит в LLM: разбор свободного текста на задачи (R9), свободные вопросы про
задачи, черновики финмоделей (R12), систематизация чатов (R10).

На LLM-ветке отправлять только ту задачу, о которой спрашивают, а не весь вольт.

## Доставка кода на ноутбук заказчика

Git и OpenClaw не альтернативы, а два конца одной трубы:

- **Git — код и конфиги, машина → машина.** Приватный remote, `git pull` запускает
  OpenClaw-инстанс на его ноутбуке по нашей команде или расписанию. Даёт откат
  («вчера работало»), диффы и защиту от частичного обновления.
- **Telegram — артефакты, машина → человек.** Excel-выгрузки, отчёты, готовые
  финмодели. Заказчик просил именно так (R8, R12 в ТЗ).
- **Каналы не смешивать.** Код через Telegram — без версий и с риском доставить
  три файла из пяти. Данные и секреты в общий репозиторий не попадают никогда.

Почему это не нарушает R5 («без сложной инфраструктуры»): если git-авторизация на
его ноуте отвалится, у заказчика ничего не ломается. Вольт — плоские файлы, движок
работает, задачи ведутся руками. Сломанная доставка блокирует обновления, а не
работу — это ровно R6.

Три хранилища, не одно:

| Что | Где | Кто пишет |
|---|---|---|
| Код + шаблоны конфигов | наш git, приватный remote | мы |
| Вольт заказчика (задачи, заметки) | его ноутбук, локальный git внутри движка | движок |
| Секреты (telethon-сессия, ключи) | только его ноутбук | ставим руками при развёртывании |

- Синхронизация вольта между машинами: git или Syncthing
- Где живёт приватный remote для кода: GitHub, self-hosted, что-то ещё
- ~~Что уже установлено на Windows-ноутбуке заказчика~~ — закрыто вопросом Q8 в
  `todos/TZ.md`: git и Python (и при необходимости Node) ставим мы руками при
  развёртывании, не силами заказчика. Этот пункт висел здесь открытым дольше,
  чем следовало, и им обосновывались решения — в том числе отказ от фронтового
  фреймворка. Довод против React/Vue остаётся (сборка, нечитаемые диффы, R5),
  но опирается он не на «Node может не быть», а на цену самой сборки
- ~~Версионирование схемы~~ — закрыто: `PRAGMA user_version` плюс ALTER по
  версиям в `store.migrate_schema`, база заказчика доращивается сама при первом
  открытии после обновления кода
- ~~Вложения-файлы~~ — закрыто: задача, шаг и шаблон умеют нести файлы
  (`attachments.py`, таблица `attachments` в `store.py`), запись базы знаний как
  владелец ждёт переезда `kb_notes` на БД. Подробности — `ПЛАН.md`, «Вне спринтов»
- Правка сохранённого шаблона: сейчас его можно только пересоздать под тем же
  именем — состав шагов и название после сохранения не редактируются. Форма для
  этого уже есть, нужен режим «открыть существующий», и заодно решение, что
  делать с прикреплёнными к нему файлами при переименовании (владелец адресуется
  именем)
- Экспорт правил повторения в RFC 5545 RRULE как формат обмена: `dateutil` уже в
  зависимостях, наше правило ложится на RRULE почти один в один, и это дало бы
  выгрузку графика в любой календарь. Внутренней моделью RRULE брать нельзя —
  в `recurrence.py` записано осознанное расхождение с RFC (клампинг «31 февраля»
  → 28-е, иначе «раз в месяц» даёт 11 циклов в год вместо 12)
- Слой агрегации из Telegram (отдельный OpenClaw-инстанс для передачи на Windows):
  формат сессии, что именно вытягивается из чатов и как попадает в вольт —
  не проектировать, пока не дойдём до этого слоя

## Напоминания

`НАПОМИНАНИЯ.md` — как трекер начинает подавать голос сам: Планировщик заданий
Windows каждые 5 минут дёргает `remind.py`, тот решает, кого показать, и отдаёт
сменному каналу. Там же разбор, что делать, если тост не появился.

Показ тоста на живой Windows не проверялся — писалось на маке. Логика отбора и
повторов покрыта тестами.

## Контракт для бота

`ИНТЕГРАЦИЯ.md` — как OpenClaw-инстанс разговаривает с движком: вызов через
subprocess, обязательный `encoding="utf-8"`, коды возврата, формы JSON по
командам, поток утренней сборки. Читать перед тем, как писать слой 3.

Там же зафиксирована дыра: **движок не умеет создавать задачи**, а R9 требует,
чтобы бот раскладывал свободный текст на задачи. Выбор между «добавить команду
движку» и «разрешить боту писать файл самому» надо сделать до начала работы над
ботом, а не по ходу.

## Контракт

`КОНТРАКТ.md` — что оболочка обязана спросить у ядра и что получит в ответ. Оболочкой
может быть страница, окно, телеграм-бот или CLI: контракт для всех один, и продукт от
выбора оболочки не меняется. Там же признаки нарушения контракта — сверяться, добавляя
новый интерфейс.

Коротко: пишет только ядро, считает только ядро, наружу JSON в UTF-8, ошибки с
указанием поля. Оболочка не вычисляет даже «просрочено ли» — показывает, что пришло.

## План работ

`ПЛАН.md` — порядок работ по спринтам с таблицей покрытия требований. Сверяться перед
тем, как браться за новую фичу: там же зафиксировано, что заморожено и почему.

## Протокол работы

`ПРОТОКОЛ.md` — журнал хода работы: что сделано, что решено, чек-листы развёртывания
и их фактический итог. Дописывать после каждого выезда к заказчику или установки на
его машину. В отличие от `todos/TZ.md` этот файл в git — процедура развёртывания
